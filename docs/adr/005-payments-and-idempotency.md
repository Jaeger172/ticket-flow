# ADR-005. Неизвестный платёж и монотонная компенсация

- Статус: принято для архитектуры MVP.
- Дата: 2026-11-07.

## Контекст

Тайм-аут провайдера не доказывает отсутствие списания. Повторы HTTP, callbacks и возвратов могут создавать двойной эффект. Поздняя команда создания может пересечься с компенсацией.

## Варианты

1. Считать тайм-аут отказом: можно отменить оплаченный заказ без возврата.
2. Всегда повторять с новыми идентификаторами: риск повторного списания.
3. Стабильные ключи, сверка и сохраняемая цель отмены.

## Решение

Orders заранее сохраняет reservationId и paymentId. Payments использует у провайдера тот же paymentId и возвратный ключ paymentId:refund. Неизвестный результат остаётся PENDING / CANCEL_PENDING до сверки. cancelRequested сохраняется монотонно; поздний CAPTURED переводит отменяемый платёж в REFUND_PENDING. Команда отмены / освобождения для ещё не созданного ID сохраняет tombstone, запрещающий позднее создание. Имитатор провайдера поддерживает отмену по merchantPaymentId с таким же правилом. Idempotency-Key связан с caller, операцией и хешем запроса; другой payload под тем же ключом даёт 409.

## Последствия

Нельзя объявить заказ CANCELLED до конечного финансового результата. Возможны длительные COMPENSATING и повторные попытки возврата; требуется видимость оператору. Гарантия одного эффекта опирается на уникальность ключей и поддержку идемпотентности провайдером, а не на брокер. Подключение реального провайдера требует проверить срок хранения его ключей и возможности отмены; при отсутствии tombstone API адаптер обязан сериализовать создание / отмену и сверять незавершённые обращения. Удаление локальных ключей не должно делать возможным новое списание по старому ID.
