# ADR-002. Orders управляет сохранённой Saga

- Статус: принято для архитектуры MVP.
- Дата: 2026-11-07.

## Контекст

Резерв, списание и выдача билета не входят в одну транзакцию. Нужно понимать, на каком шаге произошёл сбой, и продолжать после перезапуска.

## Варианты

1. Цепочка HTTP-вызовов в запросе покупателя: контекст теряется при падении процесса.
2. Чистая хореография событий: меньше центральной логики, сложнее увидеть компенсацию и согласовать поздние результаты.
3. Оркестрация с состоянием и заданиями в БД.

## Решение

Orders хранит состояние Saga и durable-задания, вызывает команды по HTTP и получает факты через RabbitMQ. POST покупателя отвечает 202 после локальной фиксации заказа. Изменение заказа и постановка следующего задания атомарны. Workers используют lease, условное обновление версии и стабильные ключи операций. Просроченный lease позволяет продолжить незавершённый шаг.

## Последствия

Есть единая точка управления процессом, но Orders становится ответственным за восстановление и компенсации. HTTP-ответ и событие могут описывать один факт: переход должен быть идемпотентен. При недоступном сервисе заказ остаётся в промежуточном состоянии. Watchdog восстанавливает зависшие шаги; принудительно объявлять успех или отмену по таймеру нельзя.
