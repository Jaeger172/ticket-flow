# ADR-001. Три контекста и собственные базы

- Статус: принято для архитектуры MVP.
- Дата: 2026-11-07.

## Контекст

Покупка связывает место, заказ и внешнее списание. У этих областей разные инварианты и причины изменений. Команда состоит из 3–4 человек, поэтому лишние сервисы увеличат стоимость реализации.

## Варианты

1. Монолит и общая схема БД: проще локальные транзакции, но не выполняет выбранную учебную декомпозицию.
2. Три сервиса по бизнес-контекстам.
3. Отдельные сервисы каталога, пользователей, билетов и уведомлений: больше развёртываний без самостоятельной необходимости в MVP.

## Решение

Выделить Orders, Reservations, Payments. У каждого своя логическая PostgreSQL-база и пользователь. Каталог остаётся в Reservations, билет — в Orders. Прямой доступ к чужим таблицам запрещён. На Java / Spring Boot можно реализовать все три приложения одним привычным стеком; UI остаётся простым.

## Последствия

Границы объясняются правилами, а не числом сущностей. Межсервисные ссылки проверяются API, общих FK нет. Появляются временно расходящиеся состояния и необходимость Saga. В демо базы могут жить в одном экземпляре PostgreSQL; production-топологию предстоит определить отдельно.
